Concrete implementation plan for Option A
1) Change the backend structure for serverless
Right now your backend is built like a normal long-running Express server ( server/server.js  with  app.listen()  and startup bootstrapping).
That won’t work directly on Vercel.
Target structure
You should split it into:
-  server/app.js  → creates and exports the Express app only
-  server/bootstrap.js  → connects DB + runs idempotent seed/bootstrap
-  server/server.js  → local dev entry ( app.listen(...) )
-  api/index.js  → Vercel serverless handler
Why
Vercel needs a request handler, not a permanently listening server.
────────────────────────────────────────────────────────────────────────────────
2) Create  server/app.js 
Move all app setup here:
-  express() 
-  cors() 
-  express.json() 
- route mounting:
-  /api/auth 
-  /api/menu 
-  /api/orders 
-  /api/settings 
- health route
- 404 handler
- error handler
Important
 server/app.js  should not:
- call  app.listen() 
- call  process.exit() 
- immediately connect to DB on import
It should only export the app.
Pseudo-shape:
// js
import express from "express";
import cors from "cors";
import authRoutes from "./routes/authRoutes.js";
import menuRoutes from "./routes/menuRoutes.js";
import orderRoutes from "./routes/orderRoutes.js";
import settingsRoutes from "./routes/settingsRoutes.js";
import { notFoundHandler, errorHandler } from "./middleware/errorHandler.js";
 
const app = express();
 
app.use(cors(/* config */));
app.use(express.json());
 
app.use("/api/auth", authRoutes);
app.use("/api/menu", menuRoutes);
app.use("/api/orders", orderRoutes);
app.use("/api/settings", settingsRoutes);
 
app.get("/api/health", ...);
 
app.use(notFoundHandler);
app.use(errorHandler);
 
export default app;
────────────────────────────────────────────────────────────────────────────────
3) Keep  server/server.js  only for local dev
Your current  server/server.js  is the right place for local dev startup, but it should become a thin runner.
New role of  server/server.js 
- validate required env vars for local dev
- call bootstrap
- start Express with  app.listen(PORT) 
Pseudo-shape:
// js
import dotenv from "dotenv";
import app from "./app.js";
import { bootstrapApp } from "./bootstrap.js";
 
dotenv.config();
 
const PORT = process.env.PORT || 5000;
 
await bootstrapApp();
 
app.listen(PORT, () => {
  console.log(`Server running on ${PORT}`);
});
This keeps:
-  npm run server 
-  npm run server:dev 
working locally.
────────────────────────────────────────────────────────────────────────────────
4) Add  server/bootstrap.js 
This is where you prepare the app for both local dev and Vercel.
Responsibilities:
- connect to MongoDB
- run seed/init logic once per serverless instance
- cache the bootstrap promise
Example pattern:
// js
import { connectDB } from "./config/db.js";
import { ensureSeedData } from "./seed.js";
 
let bootPromise;
 
export function bootstrapApp() {
  if (!bootPromise) {
    bootPromise = (async () => {
      await connectDB();
      await ensureSeedData();
    })();
  }
  return bootPromise;
}
Why this matters
On Vercel:
- functions cold start
- multiple requests may hit same warm instance
- you do not want to reconnect and reseed on every request
A cached bootstrap promise avoids repeating startup work inside one warm instance.
────────────────────────────────────────────────────────────────────────────────
5) Refactor Mongo connection caching for serverless
This is critical.
Current risk
MongoDB Atlas M0 free tier has connection limits.
If every Vercel function invocation does a fresh  mongoose.connect() , you can burn connections fast.
Fix
Change  server/config/db.js  to use a global cache.
Pattern:
// js
import mongoose from "mongoose";
 
const MONGODB_URI = process.env.MONGODB_URI;
 
if (!globalThis.__mongoose) {
  globalThis.__mongoose = { conn: null, promise: null };
}
 
export async function connectDB() {
  if (globalThis.__mongoose.conn) {
    return globalThis.__mongoose.conn;
  }
 
  if (!globalThis.__mongoose.promise) {
    globalThis.__mongoose.promise = mongoose.connect(MONGODB_URI).then((m) => m);
  }
 
  globalThis.__mongoose.conn = await globalThis.__mongoose.promise;
  return globalThis.__mongoose.conn;
}
Why
This reuses the connection inside warm serverless instances and reduces Atlas connection churn.
────────────────────────────────────────────────────────────────────────────────
6) Refactor seeding for serverless
Your current  seedDB()  was designed for one server startup.
That is not ideal in serverless.
What must change
Admin seeding
Admin seeding should be idempotent.
Good behavior:
- if admin does not exist → create it
- if user exists but role is wrong → set role to  admin 
- do not assume seed runs only once forever
Menu seeding
This needs thought.
If menu seed runs on every cold start using “if count is 0 then insertMany”, there is a concurrency risk on first deployment.
Better approach
Make seed functions safe for repeated execution:
- admin:  findOne + create/update , or upsert
- menu: ideally  bulkWrite(... upsert: true)  by  itemId 
That makes repeated cold-start seeding safe.
Important note about  ADMIN_PASSWORD 
Your current seed creates the admin if missing, but likely does not rotate the password later.
So:
- first deploy: fine
- later changing  ADMIN_PASSWORD  in Vercel may not update the existing admin password unless you explicitly code that behavior
I would keep it as create-if-missing unless you intentionally want password rotation.
────────────────────────────────────────────────────────────────────────────────
7) Create the Vercel function entry:  api/index.js 
This is the serverless handler Vercel will run.
Example shape:
// js
import app from "../server/app.js";
import { bootstrapApp } from "../server/bootstrap.js";
 
export default async function handler(req, res) {
  await bootstrapApp();
  return app(req, res);
}
Why this works
An Express app is a request handler function, so after bootstrapping you can hand the request to it directly.
No  app.listen() .

8) Fix  vercel.json 
Your current  vercel.json  is:
// json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
That is fine for SPA-only, but it will break the backend because  /api/...  would be rewritten to HTML.
Replace it with API-first routing
Recommended:
// json
{
  "functions": {
    "api/index.js": {
      "maxDuration": 10
    }
  },
  "rewrites": [
    {
      "source": "/api/(.*)",
      "destination": "/api/index.js"
    },
    {
      "source": "/((?!api/).*)",
      "destination": "/index.html"
    }
  ]
}
What this does
-  /api/*  → backend function
- everything else ( / ,  /login ,  /menu ,  /admin ) → SPA  index.html 
That preserves client-side routing.

11) CORS for Option A
Because frontend + backend are on the same Vercel project/domain, browser CORS is mostly not a concern in production.
But you still need local dev support.
Recommended CORS behavior
Allow:
-  http://localhost:5173 
-  http://127.0.0.1:5173 
And optionally your production domain / preview domains.
Better than current fixed single-origin approach
Because preview deployments may use changing  *.vercel.app  URLs.
A safer server-side CORS callback can allow:
- no origin
- localhost
- your production domain
- optionally  *.vercel.app 
If you keep same-origin only, this is less critical, but it helps preview testing.

12) Vercel environment variables
You’ll need to set these in Vercel Project Settings:
-  MONGODB_URI 
-  JWT_SECRET 
-  ADMIN_EMAIL 
-  ADMIN_PASSWORD 
-  CLIENT_ORIGIN 
Very important
Set them for both:
- Preview
- Production
Otherwise your preview deployment may build but the API will fail at runtime.
Even better
Use a different MongoDB database name for Preview than Production.
Example:
- Preview:  .../caffeine-preview 
- Production:  .../caffeine 
Why:
Preview deployments can create orders/users/settings and pollute live data if they share the same DB.

Pitfalls to watch for
1) Current  vercel.json  will break the API
Must be changed before deploy.
2) Uncommitted  /server  won’t deploy
This is the biggest immediate blocker.
3)  app.listen()  must not run on Vercel
Separate app from local runner.
4) MongoDB connection caching is mandatory
Especially on Atlas free tier.
5) Seed logic must be idempotent
Cold starts can re-run bootstrap.
6) Preview deployments can write into prod DB
Use separate preview DB if possible.
7) Cold starts
Expected on hobby/free serverless.
Usually acceptable for this app.
8) Double  /api/auth/me  fetch on  /menu 
Right now  ProtectedRoute  verifies, and  App.jsx  also refreshes user.
Not a deployment blocker, just redundant.
